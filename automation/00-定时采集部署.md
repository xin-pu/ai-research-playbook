# 定时采集部署

> 本文件是把 `ai-research-playbook` 的无人值守采集部署到云服务器的操作手册。流水线结构沿用 `optical-module-playbook` 在同一台服务器上的既有工作流：**cron → 入口脚本（锁/日志/自更新/健康检查/告警）→ `opencode run` 加载采集技能 → 只写 `.inbox` 与 `outputs/weekly` → 推送**。

## 1. 流水线一览

| 时间（服务器时区） | 入口 | 内容 |
| --- | --- | --- |
| 每天 09:00 | `automation/ai-playbook-daily.sh daily` | 过去 24 小时新资料 → `Sources/<域>/.inbox/` 投递 → 提交推送 |
| 每周日 00:30 | `automation/ai-playbook-daily.sh weekly` | 过去 7 天采集 + `outputs/weekly/YYYY-MM-DD-采集分析.md` + 汇报邮件 |
| 手动 | `automation/ai-playbook-daily.sh dry` | 只读巡检：源可达性、待合箱清单、仓库边界；不写不发不提交 |

- 采集工作流本体在 `.opencode/skills/ai-research-collect/SKILL.md`，入口脚本只负责运行环境与判据。
- 入口脚本每轮先 `git pull` 再 `exec` 自己（自更新），因此**改技能或改脚本，下一轮定时运行即生效**。
- 每个任务用独立锁 `automation/.collect.lock`，与同一服务器上其它 playbook 任务互不阻塞；锁被占用时本轮跳过并记日志。

## 2. 服务器一次性准备

沿用该服务器已有的准备工作（`my-email` 工作流装好的东西不用重装）：

1. 运行时：`opencode`（`~/.opencode/bin`）、`jq`、`flock`（util-linux 自带）、`poppler-utils`（`pdftotext`，`dnf install poppler-utils`）。
2. 密钥：`~/.secrets/qwen.env` 提供模型密钥（600 权限，不进仓库）。
3. 仓库部署：内容仓库克隆到 `~/ai-research-playbook`，并配置可推送的 deploy key / remote（SSH over 443 的做法沿用 `my-email` 的约定，不要用 HTTPS 推送）。
4. 邮件通道：`ms365` MCP 在 `opencode` 全局配置里可用且已登录（`my-email` 工作流已登录，同一台机器可复用）；汇报与告警都走它。
5. cron：`bash automation/install-cron.sh`（幂等，已有条目不动，改动前备份 crontab）。

一次性核验：

```bash
cd ~/ai-research-playbook
bash automation/check-egress.sh        # 出口可达性：把结果回写 SKILL 3.0.1 两
bash automation/ai-playbook-daily.sh dry   # 只读巡检档，验证锁/日志/健康检查链路
bash automation/ai-playbook-status.sh      # 看日志与 health 文件
```

## 3. 首轮必做：回写可达性表

`.opencode/skills/ai-research-collect/SKILL.md` 第 3.0.1 节的可达性表分两部分：同服务器继承（GitHub API、Bing、npm/pypi、crossref 等，来自 optical 工作流 2026-10-09 实测）与 AI 系来源首测状态（arXiv、Hugging Face、OpenReview、Semantic Scholar 等，标「待首测」）。

**部署后第一轮先跑 `check-egress.sh`**，把实测结果回写该节：长期不通的移入「不可达」清单（禁止浪费超时），新通的补进可用表。换机器或某个域连续两轮采不到东西时重复这一步。

## 4. 健康判据与日志

- **成功与否看产物，不看 `opencode run` 的退出码。** `opencode run` 在任意一次工具调用报错时都以 1 收尾（采集撞 403/超时属常态），据此判失败会天天误报。
- 每轮产物：`automation/logs/collect-<mode>-<时间戳>.log`（原始日志）与同名 `.health`（PASS/FAIL 判据）。
- 健康检查项：
  1. 仓库边界：改动只允许出现在 `Sources/**/.inbox/**` 与 `outputs/weekly/**`；
  2. 推送：无未推送提交（未设 upstream 时记 INFO 不判失败）；
  3. daily：记录新增投递文件数（0 不判失败，可能是确实没有新内容）；
  4. weekly：本轮必须写出 `outputs/weekly/<运行日>-*.md`；
  5. dry：必须生成巡检报告，且不产生任何投递文件。
- 不健康时退出码 2，并按 `automation/config.json` 的 `reportTo` 发告警邮件（dry 档不发信）。cron 汇总日志在 `automation/logs/cron.log`。

## 5. 边界与分工

| 谁 | 写什么 |
| --- | --- |
| 服务器采集代理 | `Sources/<域>/.inbox/**`、`outputs/weekly/**`，仅快进推送 |
| 本机人工主流程 | 合箱（`.inbox` → 箱 + `E<编号>`）、域导航页、`Sources/update-log.md`、`knowledge-base/`、规则文件 |

- 冲突时技能执行 `git rebase --abort` 保留本地提交并在邮件里写「推送未成功，需人工合箱」，**不强推**。
- `.inbox` 中的内容视为未入箱状态；超过一周未合并必须显式关闭或删除（见 `Sources/归箱规则.md` §9）。

## 6. 常用操作

```bash
bash automation/ai-playbook-status.sh          # 最近日志 + health + 待合箱 + 仓库位置 + crontab
bash automation/ai-playbook-status.sh --log 80 # 多看点日志
AI_PLAYBOOK_NO_PULL=1 bash automation/ai-playbook-daily.sh daily   # 用当前检出跑一轮（调试）
AI_PLAYBOOK_DAILY_CRON="0 9 * * *" AI_PLAYBOOK_WEEKLY_CRON="30 0 * * 0" bash automation/install-cron.sh  # 改时间
```

停用：`crontab -e` 删掉含 `ai-playbook` 的两行（或删掉 `automation/logs/crontab.bak.*` 之外的对应条目）。

## 7. 与 optical 工作流的差异

- 没有 Documize 镜像环节（本库不镜像到 Documize）；周度产出就是 `outputs/weekly` 分析 + 邮件。
- 采集是**每日**档 + 每周分析档（论文节奏快），optical 是纯周度。
- 服务器只投 `.inbox`：本库的合箱、导航与台账维护在本机进行，与 optical 相同。
